# security/sbom/ — Trivy / SBOM artifacts

Generated by `security/trivy-scan.sh` (or `.ps1`) and committed so the
scan's actual output is reviewable without re-running the tools — the same
"artifact, not just a script" posture as `database/seed_data.sql` or the
dashboard's `data.example.json`.

| File | Tool | What it is |
|---|---|---|
| `trivy-fs-report.txt` | `trivy fs` | Dependency vulnerabilities (`requirements.txt`) + misconfigurations in the Dockerfile, `helm/`, `kubernetes/`, and `policies/kyverno/testdata/` manifests. `terraform/` is excluded — already covered by Checkov (`.checkov.yaml`), see the script's own comment for why running a second, differently-tuned IaC scanner over the same files would just add noise instead of coverage. |
| `trivy-image-report.txt` | `trivy image` | OS packages + Python dependencies actually baked into the `automation-controller:local` image built from the repo-root `Dockerfile`. |
| `automation-controller.cdx.json` | `trivy image --format cyclonedx` | CycloneDX SBOM of that same image. |
| `automation-controller.spdx.json` | `syft` | SPDX-format SBOM of the same image (two formats committed since different downstream tooling expects one or the other). |

## Severity policy

Same hard-fail/soft-fail split as `.checkov.yaml`: CRITICAL findings fail
the script (and the CI job in `.github/workflows/security-scan.yml`);
HIGH/MEDIUM/LOW are reported in the `.txt` files but do not block.

## Real findings from the last run (not invented, not scrubbed)

- **Base image (`python:3.11-slim`, Debian 13) OS packages**: several
  HIGH/MEDIUM CVEs in `perl-base`, `util-linux`, `ncurses`, etc. — upstream
  Debian package CVEs, no CRITICAL. Mitigation available: pin a newer
  Debian point release or move to `python:3.11-alpine` (smaller surface,
  different libc — not done here to avoid an untested runtime change
  outside this session's scope).
- **Python dependencies**: HIGH on `wheel==0.45.1` (CVE-2026-24049) and a
  few `pip`-bundled CVEs — these ship inside the base image's own `pip`,
  not from `requirements.txt` directly pinning a vulnerable version.
- **Dockerfile**: 1 LOW (`DS-0026`, missing `HEALTHCHECK`) — deliberate,
  see the Dockerfile's own comment (liveness/readiness are owned by
  Kubernetes probes, not Docker's `HEALTHCHECK`, to avoid two disagreeing
  health signals).
- **Helm chart**: was 13 failures (3 HIGH, 4 MEDIUM, 6 LOW) before this
  session hardened `helm/automation-controller/templates/deployment.yaml`
  with a real `securityContext` (non-root uid/gid matching the Dockerfile,
  `readOnlyRootFilesystem`, dropped capabilities, seccomp profile). Now 1
  MEDIUM remains (`KSV-0125`, "image from an untrusted registry") — a
  false positive against Trivy's default trusted-registry allowlist,
  which doesn't include `ghcr.io` out of the box; not suppressed here
  (would need a `.trivyignore` + justification policy out of this
  session's scope), just documented.

## Regenerating

```bash
bash security/trivy-scan.sh          # fs + image + both SBOM formats
bash security/trivy-scan.sh --fs-only   # skip docker build/image scan
```

Requires `trivy` on PATH always, plus `docker`/`syft` unless `--fs-only`.
